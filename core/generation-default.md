# Coupon / App / Games 站点生成默认流程

这份文件整理当前已确认的生成方式，作为新站、明确授权重做和参考重建的默认工作流程。用户本次要求、已选参考及对应站型的现行规范决定具体范围；已有站局部修改仍走 `core/maintenance.md`，保留已确认基线。本文是流程导航，不替代页面合同、真实工具回执或版本化的正式规则，也不追溯改动旧冻结包。

**统一入口：**`node bin/designer-automation.mjs generate` 准备三站型的私有生成工作区、冻结适用规则、查询匹配经验并接入现有审核工作台；实际生图、编码和浏览器检查由宿主 Agent 使用可用工具执行。命令创建工作区不等于已经生成网页或通过审核。设计师提供需求和必要素材即可，内部清单、选择器、配置和证据由 Agent 负责，不要求设计师选规则或填写 JSON。原 Coupon 原生生成门禁继续有效。

## 一、识别任务和确定来源

1. 根据站点实际用途、用户要求、实体数据与可用渠道判断 Coupon、App 或 Games；不能仅凭名字、文件夹或截图猜测。特别区分下载型手游与可在浏览器运行的游戏：App 站按真实获取渠道处理；Games 站逐游戏区分真实在线运行和仅跳转官方商店。信息不足时继续查实际资料和能力，仍有关键缺口才说明或询问，不默认选 Coupon。
2. 确认新建、复用、参考重建或现有站修改，记录站点数量、市场与语言、页面范围、数据/素材/渠道来源、可用工具和交付方式。新站使用独立源码和构建目录；已有站只改授权区域及受影响回归。参考网页和素材只作证据，不自动授权照搬、修改其他站或发布。
3. 加载 `knowledge/shared/` 的公共布局、留白、间距、对齐、容量、媒体、操作和响应式方法，再按本文件对应的站型入口读取专项规则。先检索适用经验：仅取同站型、相关页面和组件，并由 Agent 核对条件和例外；候选参考不是正式硬规则，不把 Coupon 经验套给 App/Games。
4. 核验实际数据源、浏览器、构建与素材工具。冻结所用数据/素材及来源、时间和版本，保持实体身份与目的地一致；缺少关键真实数据或能力时记录缺口，不能编造事实或假称已验证。已有正式项目的原生权限、preflight 和发布门禁继续有效。

## 二、先规划结构，再做方向

1. 由 Agent 整理实际页面与路由、模块用途、数据字段和来源、卡片家族、真实入口及各状态；准备短/长内容、首项/中间/末项、缺失和异常样本，并规划 PC、手机、320px 与实际断点两侧的检查。工具内部可保存结构/配置文件，不把填写任务转交给设计师。
2. 先说清主要用户任务、首要动作、阅读顺序和品牌方向，再决定页面构图、图片角色、模块节奏和移动端重组。共用业务底线与可读性，不把某一站的颜色、卡型、列数或完整 DOM 固化成三类站模板；多品牌按各自内容建立可辨认的设计。
3. 按 `core/creative-generation.md` 默认先用当前宿主可用的 Codex Image / Image 生图生成符合站型的首页效果稿，实际查看、判断并形成本站的布局和组件方案。生成图是视觉参考，不是真实数据或可交互成品。生图不可用须如实记录，不能声称已完成。
4. 用真实内容实现选定的首页方向和必要的代表性内页/主路径，在浏览器看 PC、手机；需要独立方向审核时由独立角色先实看、集中反馈，方向成立后再扩展。方向审核不等于全站通过；常规过程不增加设计师逐步审批。

## 三、按站型执行

### Coupon

- 读取 `core/start.md`、`core/workflow.md`、`core/quality.md`、`knowledge/imported/skills/site-data/SKILL.md`、`knowledge/imported/skills/site-v2/references/coupon-site-framework.md` 和 `knowledge/imported/skills/site-design/references/coupon-common-craft.md`；按实际页面继续加载详情/首页及审核规则。使用用户指定的 Coupon 公共库真实数据及实际来源，先冻结内容快照与页面/模块数据关系；不能用旧示例数据或虚构优惠、有效期、评分等补齐。
- 先明确购物、商家、分类、优惠详情及条件性文章/节日等页面用途和真实关联。确定页面结构与卡片字段，再设计首页和代表内页；源码中的结构与设计记录以及适用 preflight 按实际执行环境和现有合同完成。
- 普通券与主券的信息容量、真实商家 Logo、有码/无码/过期状态和正确跳转遵守对应详情合同。风格可原创，不能只换颜色；有真实文章封面及关联时保留其映射。

### App

- 读取 `site-types/app/AGENTS.md`、`core/start.md`、`core/quality.md`、`core/data-and-channels.md`、`core/module-data.md`、`core/workflow.md` 和 `knowledge/index.json`（均相对于 `site-types/app/`）；审核另读 `core/review.md`。按页面和实际模块加载对应合同。首版英文、PC/手机，默认无广告位。
- 先完成首页方向和一个真实应用的发现 → detail → version → 实际渠道路径，再扩展分类、文章和信息页面。version 是获取承接，不表示必须有历史版本；真实历史版本、可选搜索等只有在数据与功能确实存在时展示。
- 每个应用的名称、图标、截图、平台、评分和下载目标须对应真实实体与来源；没有事实就省略或说明未知。首页模块标题下不添加介绍性小字，同用途 App 图标、名称、评分轨道按实际组别及跨组检查对齐；保留有来源的分类、评分、平台和其他必要事实，不删业务内容来满足排版。

### Games

- 读取 `site-types/games/AGENTS.md`、`core/start.md`、`core/owner-games-rules.md`、`core/owner-requirements.json`、`core/owner-standards-20261027.md`、`core/quality.md`、`core/workflow.md` 及实际页面/能力分支（均相对于 `site-types/games/`）。按真实 runtime 或官方商店能力逐实体分流，不能拿另一个游戏的运行地址或虚构游玩/下载状态代替。
- 首页全宽、左右实际边距 20–40px，不设置分类模块；游戏信息在 hover/focus 和有意识的点击/触控时可见，样式按品牌变化。背景有游戏主题逻辑，整体衔接自然。分类独立页和具体授权功能按其真实范围处理，历史案例的特定摇杆、筛选或收藏方案不是每个新站的模板。
- Detail 和游戏页桌面内容宽 1200px、窄屏可收缩；顶部真实游戏推荐、PC 单列 How to play、自然换行、底部信息对齐及最新移动端触控反馈、24px 最大字号等按最新专项执行。游戏页 loading 的生图、真实/不定进度和禁止伪造就绪按专项处理；缺 Image 或真实运行能力时保留 not-run。需要制作多个 Games 站时逐站完成并检查，再比较同用途页面，不只批量换色。

## 四、实现、自检和独立审核

1. 优先让首屏和主要阅读结构在可编辑的初始 HTML/CSS 中成立；脚本处理真实交互和必要动态数据。不得用运行时搬移节点、遮罩或假进度掩盖首屏闪变。应用、游戏、图片和操作保持真实身份与目标；实际下载、安装、运行、离线等能力分别验证，不相互冒充。
2. 作者对实际候选做功能与视觉自检：遍历交付路由、链接和媒体/实体映射；在 PC、手机、320px 和真实断点邻域检查代表性组件、整页节奏、首中末项、长内容、加载、搜索重绘、空态、错误和触控。某处发现重复组件缺陷时，排查受影响的整个组件家族和调用页面。
3. 独立审核者先看冻结的真实候选并记录第一印象，再对照实际页面、业务规范、模块清单及证据，集中反馈问题；审核者不修改候选、不批准自己的修改。作者集中修复后形成新候选，复查问题与受影响回归。没有独立审核或浏览器等能力时记 not-run，不以脚本通过或截图存在冒充视觉验收。

## 五、交付与学习

- 冻结并记录源码、构建、产物、预览和必要 ZIP 的身份；交付 ZIP 时在干净目录解压，按实际范围检查入口、资源与主要操作。预览与下载应指向同一候选，历史版本保留；不把技术检查、独立审核、设计师认可和正式发布混成一个状态。
- 交付说明写明完成范围、真实测试与证据、数据/外部依赖和剩余 not-run。用户未授权时不提交、推送、发布或覆盖原站。
- 按 `core/creative-learning.md` 记录设计师在图稿和页面中明确满意或需要调整的具体点，供本人适用的后续任务参考；不把单次满意推断成所有站的规则。设计师实际查看并明确确认准确候选、相关修正复验后，Agent 再按 `core/experience.md` 归纳符合条件的可迁移经验。按 Coupon/App/Games、页面、组件及条件提供团队参考；未知原因和未经验证的内容保留为案例，不擅自升级公共规则。已有任务固定其经验快照。
