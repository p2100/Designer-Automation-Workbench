# 学习设计师的创作与反馈

`core/creative-generation.md` 是三类站点的默认创作方法，不是固定皮肤。设计师在自己的 Agent 上创作时，Agent 应根据本人真实表达的满意之处和修改意见，逐步理解其在特定场景下的判断；新需求、站型业务规则及明确指定的参考始终优先。

## 什么时候记录

- 设计师对实际看过的首页稿、内页稿、组件或真实候选明确表示喜欢、保留或不满意时，记录具体对象和原意。可以是页面层级、卡片内信息分组、按钮、颜色关系、图片与文字的组合、留白或手机重组，不限于程序发现的错误。正向记录为 positive-reference，明确否定记录为 avoid-reference；后续任务按时间、组件、站型和条件判断，不能把旧偏好当成当前设计师始终认可。
- 一个整体“可以”只表示对当时对象的认可，不自行推断每个颜色、模块都受到偏爱，也不替设计师认定整个站已经通过。若对象或原因不清楚，保留原话与上下文为待理解记录；不强行编出“设计师喜欢某风格”。
- 方向稿阶段的喜欢只适用于那份图稿及指定部分，不等于真实页面通过或该站已验收。真实页面修复经验的共享仍需准确候选、实际复验及设计师确认，遵循 `core/experience.md`。设计师无需手填经验表或 JSON。

## Agent 怎样提炼

每次从实际反馈提炼一个可理解的观察，保留足以追溯的最小上下文：

1. **对象和来源**：实际站点类型、页面、组件、桌面/手机、图稿或候选身份，以及相关反馈原话或准确摘要；仅保存任务需要的内容，不复制整段聊天、密钥或私密链接。
2. **具体设计点**：例如“这张首页重点卡的图文分组清楚”，说明真实可见的图片、文字、动作或留白关系；没有明确原因时写“原因待理解”，不虚构设计师的心理或效果数据。
3. **适用边界**：这是本次品牌的选择、本人反复表达的偏好，还是经过多个场景检验的可迁移方法；记录适用站型、页面、组件、条件和不适用情况。示例仅用于说明记录粒度，不是预先写入的经验。
4. **状态与后续**：区分原始反馈、单次已表达的偏好、可供个人任务参考的观察、满足共享经验条件的结论，以及被纠正或撤回的旧观察。记下已做的修改与真实复查；未经实际确认不能写成设计师认可。

新反馈出现时先查已有记录，补充新的证据和条件，避免每次对同一想法另建一条；如果实际表达不同或设计师改变想法，保留旧记录与变化，不偷偷合并成一个相反的结论。不要凭关键词近似自动断定重复。

## 在本人后续任务中使用

Agent 把设计师针对已登记图稿或候选的实际反馈、准确摘录、页面和组件记录在本机。系统按站型将摘录、观察和稿件指纹自动排队同步到中央团队库，不上传整段聊天或图片；其他电脑的新任务会检索同站型、页面参考。离线或服务尚未升级时记录保留并重试，待传不是已共享。历史本机有效记录会在更新后自动补传；证据缺失的记录不会上传。单独表扬不批准整站。

团队创作参考是主观意见，Agent 应核对适用组件及具体条件，不作为强制规则，也不混用 Coupon、App、Games。创作参考目前为追加记录，新纠正与旧意见并存，Agent 按时间和具体对象判断；尚无单条创作参考撤回工具。姓名是记录声明而非身份认证。正式修复经验仍遵守复验和确认门禁；不能编造设计师意见或审美认可。

## 从个人观察到团队经验

- **先保留**：真实满意点和修订意见可以在创作过程中记录；如果只有方向稿、没有复验或没有清楚确认，就保留为参考材料，不能标成已共享的有效结论。
- **再验证**：在真实页面和适用设备上检查是否有助于阅读、容量和操作，并记录实际结果。不能因为喜欢某张效果图就宣称真实页面或其他站均有效。
- **按现有能力共享**：适合团队的修复经验走现有 MCP，绑定站型、页面、组件、条件、真实复验及准确候选确认。ZIP 站的符合条件结论可作为同类型候选参考；其他 Agent 仍须判断适用性。站点专属审美偏好保留在相应范围，不自动传播到其他站型。
- **正式规则另行维护**：多个真实案例支持的方法才可按既有规则流程考虑升级；个人偏好不静默覆盖业务硬要求或公共规则。

**实现边界：**Agent 负责理解原话和判断适用性；程序验证绑定并按站型、页面检索，不能证明对话真假、设计质量或身份。团队参考与审核规则分开；没有真实反馈时不预置偏好。
