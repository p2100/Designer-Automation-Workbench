# 经验的提炼、复用和纠错

这是维护流程的经验规则。原生成规范、业务硬要求和独立审核门禁继续以冻结规则包为准，经验不能改写它们。

## 什么时候提炼

只提炼真实修复中已经确认、未来能复用的判断或方法。每条只讲一个问题，包含：具体问题、已确认原因、可执行的预防方法、适用页面和组件、触发条件、已知例外、实际复验项以及设计师对准确候选的确认。用户说“OK”是本次版本的认可，不能推导为所有站点、所有页面、所有品牌的通用规则。

未知根因、一次性文案/内容替换、偶发数据、没有新增结论的重复操作，不强行编经验。Agent在approve反馈中写learningDecision={action:"skip",reason:"具体原因"}，保留事实与理由即可。不要让设计师额外操作，也不要把“符合规范”“下次注意”“保持美观”等空话变成规则。普通对话只存相关反馈，不整段复制聊天、源码、私密地址或附件。

## 如何避免重复和冲突

先用experience_search按site、pages、component、key或query检索，必要时includePending=true查看待验证/撤回结论。比较适用条件和预防方法的语义，而不只比较标题。相同原则复用已有稳定key及规范表述，把新案例作为补充证据；key不得包含任务ID、日期、候选哈希或个人名字。服务端按key/精确原则及作用域合并，并不声称能自动理解任意语义相近的文本；语义比对由执行任务的Agent负责。

不同结论不能通过随意换key绕过已有经验。相同主题出现不同方法时，新提议保留为conflict，不覆盖已确认结论。Agent说明差异并使用experience_manage inspect查看证据/版本；确需纠错时，用已确认的新案例、expectedRevision、实际设计师身份与原因执行replace。旧版本进入history，不再同时作为当前结论返回。错误结论可直接retract，无需维护者。陈旧版本的修改会拒绝，不静默覆盖别人刚作的调整。

服务端还会识别相同明确预防方法、条件及例外的重复记录。已撤回或替换的旧原则保留历史指纹，不能仅换一个key就再次生效。

## 作用域与推广

每条lesson显式给pages或checkIds，component及learning={key,when,exceptions,transferable}。程序从这些真实复验项推导页面，不把整个任务的页面全部挂进去。无对应复验的页面不能学习该结论。建议同时给准确checkIds，避免把同页无关模块也视为依据。

第一次确认后先在来源站点、页面与组件条件内生效。明确可迁移、附真实复验和设计师确认的经验，同时可以作为后续同站型、同页面的“参考”，由Agent判断实际组件、条件和例外；参考不自动成为必修规则。相同原则在至少两个可核验的独立来源站点得到复验和认可，才按现有机制自动激活通用经验。Git SSH/HTTPS地址和.git后缀会归一化，同一仓库换个连接地址不算第二个站点。单站风格偏好不推广。

经验复用重点是后续同类型站点。来自 ZIP 或本地源码、符合确认与复验要求的可迁移结论可进入该站型的待验证参考；本地来源标识绑定本机和路径，不能证明来源独立，因此本地副本不计入自动激活通用经验的独立站点数量。不得凭本地副本或 ZIP 自述标识推测独立来源。客户端先检查中央服务是否支持本地参考；旧服务时记录保留在待传队列并报告未共享，服务升级后自动补传，不能声称已经生效。

新任务使用实际页面键查询含待验证状态的经验；只把有准确确认的同站型、同页面可迁移候选作为 reference-only，排除撤回记录。Agent 继续核对组件、触发条件与例外，不能把参考当成正式规则、设计师认可或独立审核通过。正式公共方法仍通过 Git 维护。

同站具体结论优先于对应通用结论；撤回/纠正某个支撑结论时，依赖它的旧通用结论同时失效。恢复通用结论需要至少两个独立、匹配的新证据，不能只凭一次修改重新推广。通用规则的正式升级另走Git版本管理。

## 传输与确认

workbench把确认和完整待传记录写进同一个原子持久文件，之后才调用MCP。Agent或命令在中间退出，下次MCP启动会恢复；持续运行的本地MCP也定期检查新待传记录。服务器回执落盘并更新任务状态后才清理队列。

queued不是已共享；candidate是证据/未满足要求的提议；conflict需处理分歧；shared=true表示当前有适用的有效结论。experience_status提供待传与坏记录信息，experience_manage inspect提供结论、历史和关联案例。普通反馈和skip不进入有效经验查询。

网络失败由后台自动重试。监督进程在Agent关闭后继续运行，补传子进程异常退出会重新启动；坏记录保留原文与原因，其他记录继续。整机关闭或整个监督进程被外部终止时，记录仍在磁盘，下次MCP启动恢复。旧版缺少明确作用域和学习字段的记录保留为证据，不能猜测后自动升级为通用规则。

## 工具输入示例（由Agent填写）

approve反馈中的一条lesson：

```json
{
  "summary": "状态文案变化时保留按钮所在操作区",
  "cause": "状态切换后操作区重新分配宽度，造成相邻内容位移",
  "prevention": "在该组件已验证的状态间保持操作区占位，并检查长短状态文案",
  "classification": "general",
  "component": "offer-action",
  "checkIds": ["实际任务中的检查ID"],
  "learning": {
    "key": "action.state-layout-stability",
    "when": "该组件的按钮状态切换会改变文案长度时",
    "exceptions": ["未经复验的其他组件和页面不据此修改"],
    "transferable": true
  }
}
```

示例不是已验证经验，也不是要求所有按钮统一尺寸。实际字段必须来自当前任务的修复与确认。

## 三站型的作用域

现有 designer_experience MCP、MongoDB、幂等、设计师准确候选确认、两独立来源站点激活与离线自动补传机制保持。workbench 自动把 App/Games 的经验页面键写为 app:home / games:detail 等，并以同样键查询，防止同名页面和组件跨站型误套。Coupon 保留原页面键，已有记录无需迁移。先根据实际产品、源码与页面确认站型，模糊或冲突时由Agent继续核查，不默认 Coupon；再冻结对应 contexts。Agent 直接调用 MCP 时也使用对应站型的页面键和 includePending=true，并只参考符合上述条件的 candidate；设计师不手填。通用布局/留白/间距方法在 knowledge/shared 正式规则中维护，不因个人经验放宽业务硬要求。
