# Restore first, then refine

Use this workflow when the user asks for a reference restoration, a 1:1 baseline, or an improved version after copying a reference. It is distinct from inventing unrelated visual variants. The user's actual scope and exclusions remain authoritative.

## Restoration

Inventory the source site by page family and generation. Do not mix an old detail template with a new-generation home/search unless requested. Work site → page → module. Save the actual source URLs, viewport, current HTML/style cascade, font loading evidence, assets and full-page observations. A declared font family is not proof that the face actually rendered.

A faithful restoration covers more than column widths: canvas, typography, header/footer, image roles, ordinary cards, heading relationships, inner/item/section spacing, actions, responsive order and relevant states all need evidence. Prefer measured source rules to a generic base stylesheet. A general visual-distinction rule does not require inventing novelty inside a user-requested restoration baseline.

Make an explicit differences list for authorized omissions and factual substitutions. Do not restore advertising/video whitespace, fake downloads, substitute Play, unsupported APKs or invented ratings. Real facts remain attached to their own platform/region/date. Reference artwork and current official store artwork have different provenance; label them correctly. Replacing text can change absolute scroll positions without changing the reference layout.

Do not reproduce broken media, duplicate IDs or capacity errors introduced by your generation. HTML width/height attributes must not override an intended responsive aspect ratio. A named featured-card family must survive extraction; taking only the first ordinary card is not sufficient. Source usability weaknesses may be documented in a restoration-only study, but must be clearly separated from new generation defects and addressed in the refinement.

Independently compare same-purpose, same-entity pages at equal desktop/phone dimensions. Inspect all declared page/card families and full flows to the footer, narrow and long cases. Measure base layout separately from a pulse/hover transform. Record CSS viewport, document client width and exported raster dimensions separately; retain raw screenshot bytes and never silently claim resized pixels are original CSS dimensions.

Repair author defects, freeze the restoration source and full candidate inventory, then bind independent observations to that exact baseline. Earlier evidence is not silently upgraded after rebuilding.

## Refinement

Start only after the restoration baseline is frozen. State the visitor, task, source problem and expected improvement. Give each refinement its own shell, templates, styles and behavior adapter. It can start as a copy of the frozen source, but must not keep importing the restoration's visual renderer and merely change tokens.

Share factual schemas, identity-safe formatting, media resources, game bundles and small behavior contracts. The shared builder may orchestrate routes/assets/hashes; it must not choose every site's visual shell or detail structure.

Judge improvements against the frozen baseline on desktop and phone. Ignore color, radius, shadow and decorative button treatment: useful grouping, reading order, image/text relationships or action ownership must still demonstrate a difference. Include ordinary catalogue cards, related games, details and play/information families, not just one hero. Keep familiar task controls where they already work; novelty alone is not improvement.

Verify real interactions and truthful content after regrouping. A runtime document load is not gameplay; a correct href is not a completed store transaction. Freeze the refined candidate, independently inspect it, repair and check exported copies in a clean directory. Deliver the restoration and refinement separately so the user can inspect both.

## Recording mode

Add human-readable mode/baseline/improvement notes to the task and per-site contract. Include source URLs, page-family map, exclusions, baseline candidate digest, proposed changes and evidence requirements. The current CLI's integrity checks validate task shape and bound records; they do not infer restoration fidelity, verify an external baseline automatically, determine visual distinction or certify that an improvement is useful. Those remain agent/reviewer work supported by actual evidence.
