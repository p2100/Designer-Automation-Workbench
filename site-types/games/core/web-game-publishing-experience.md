# 即点即玩 Game 站：发布与审查经验

适用于接入 SP 的即点即玩站点的新建和已授权维护。以当前项目实际配置和确认稿为准；不自动修改已冻结站点，也不把 Playaro 的视觉皮肤复制到其他品牌。

## 路由和数据

1. 从正式源码、SP 内容数据和站点配置确认站点简称、游戏身份、封面、内容、详情页及可运行游戏之间的对应关系。标题、图片、详情和游戏必须属于同一款游戏；不能仅凭 HTTP 200 断定可玩。
2. 在需求确认采用 RS/Playaro 路由规则时，详情为 `/game/detail/{游戏文件名}`，LP 为 `/game/lp/{封面文件名}`。LP 沿用约定的首页结构，将路由对应游戏置顶；详情的主按钮进入同一游戏的游玩页。实际文件名分别来自内容和封面，不能假定两者相同。其他项目的路由以其已确认配置为准。
3. 同步检查首页、推荐、搜索、详情、游戏页及 LP 的所有链接和 canonical；保留已对外使用的旧地址兼容，确认查询参数和 SP 后端探测方式仍可用。更新 SP 的 `site_lp_config` 与对应匹配规则，核对站点、路径、启用状态、`gen_api` 和匹配模式；数据库显示正确不等于接口或 Worker 已支持。
4. 有顺序依赖时先让网站、API 和异步 Worker 同时支持新旧路径，再切换数据库；用真实任务、回调与消费方检查完成整条链路。没有执行的环节记为未验证，不伪称通过。

## 多语言与接口返回

1. 从 SP 的站点语言配置读取真实启用项。按站点已配置的域名/语言机制处理，不猜测所有品牌都使用同一种子域名；没有启用或不可访问的语言要明确报错或记录缺口。
2. 在提交任务时保留投放语言，并在任务派发前持久化，避免异步任务先于请求快照运行。单语言任务返回该语言实际站点地址，英语也须在不同浏览器语言下仍显示英语；多语言任务提供逐语言地址，不悄悄挑选其中一个作为全部语言的地址。
3. 审查任务状态、LP/详情、`source_url`、回调与 path-only 结果是否一致；检查所选语言、最终 URL、页面实际语言、游戏名称/图片、首卡和游戏内语言。浏览器缓存、Cookie 和 `Accept-Language` 会影响结果，应使用不同语言和干净状态复测；不要仅靠地址前缀或 HTTP 200 判定翻译成功。
4. 至少覆盖主语言、日语、另一语言、多语言选择、未启用语言、旧任务/旧链接和失败状态；完整站点验收要逐项核查所有启用语言。确认各语言域名路由与证书可用、静态文案和内容翻译已发布，并记录结果。

## 首页 TDK 与站点原创说明

1. 收集用户为当前站点指定的首页 title、description 和 keywords，按原文写入主语言的实际 HTML `<head>`。校验解析后的文字与用户给出的内容一致，确保标签不缺失、不重复，正确转义特殊字符；canonical 和其他页面各自的标题、描述保持正确。具体关键词和品牌名称只属于当前站点，不复制给其他新站。
2. About、Privacy、Contacts 和首页介绍使用该站点自己的原创文案，按用户确认的产品定位和已核实事实撰写，不沿用参考站名称、品牌或自相矛盾的归属说明。对“自研”表述保留依据：站点文案由本团队编写、游戏文件的托管来源、游戏本身的开发和权利归属是不同事实；不能仅凭文字或外部托管地址推断所有游戏的开发者。隐私说明仍应如实描述实际运行的外部文件、服务、浏览器存储及分析工具。
3. 站点完成换牌后，逐一搜索首页、信息页、详情页、LP、可见属性、元数据及内容 API 返回的用户可见字段中的旧站名；按项目实际启用语言同步翻译并检查残留。源码中的历史来源记录用于追溯，不能为了消除页面显示而篡改来源或去掉必要的真实归属。若游戏内部画面或素材无法逐一核查，单独记为未验证。
4. 先在生成制品中检查所有受影响路由和语种，再在测试及正式环境分别抽查实际响应、精确 TDK 与页面可见文字；报告浏览器语言、缓存和范围。源码正确、翻译文件存在或 HTTP 200 均不能单独证明线上内容已更新。

Playaro 的 2026-10-30 指定首页示例是 `Free Online Games – Play Puzzle, Arcade & More | Playaro`；对应 description 与 keywords 以当次用户原文和正式源码为准。此次在 21 种语言的首页及 About、Privacy、Contacts 检查旧站名；不把这次结果推广为游戏内部画面或其他站点的验收结论。

## 根目录文件与广告标签

1. 正式站发布前明确搜索引擎收录策略，检查根域名 `/robots.txt` 返回 HTTP 200、`text/plain` 和完整的实际规则；逐一核对启用的语言域名，确认没有 CDN 自动添加的冲突或限制。用户指定允许全部抓取时，按确认的内容逐字提供；Playaro 的确认内容为 `User-agent: *`、`Allow: /` 两行。这个示例不自动替代其他站点已确认的策略。预览和测试环境按各自要求禁止索引，并检查响应头及页面 robots meta；`robots.txt` 本身不能保证页面不被索引。
2. 广告接入适用时，从本站开站记录及实际广告账户核对发布商 ID 和具体标签，不复制示例站 ID；确认根域名 `/ads.txt` 的授权行、关系类型和认证 ID 与实际账户一致。GET 和 HEAD 应返回 200，GET 为可读取的纯文本；不得以错误页或仅本地有文件当作完成。
3. 按本站广告平台及用户确认的范围，在实际页面 `<head>` 放置正确广告标签，检查首页、详情、LP、游玩及信息页和启用语言，校验账号、加载地址和重复标签。账号未确认、账户未开通或适用性不明时记录缺口，不猜 ID 或宣称广告审核通过。页面标签、游戏 iframe 内广告和 GAM 广告位是不同链路；送审或广告位应关闭时保持对应占位及渲染状态，不擅自启用广告位。标签本身可能受广告平台账户配置影响，实际展示与 Google 审核结果须另查。
4. 追踪根文件在正式部署链中的来源和覆盖行为：SP 页面生成、Worker 资源目录清理、CDN/Cloudflare 托管 robots 和缓存都可能覆盖或合并文件。Playaro 曾在 SP 发布时重建 `public/` 并删除其中的 `ads.txt`，页面生成成功也没有更新实际线上模板；因此修复要保存在可持续的正式源码和部署链中。不要把本地的 Worker 实现机械复制到其他项目，先确认该站真正的路由及资源机制。
5. 发布后直接回读正式域名和实际语言域名上的根文件、响应头、页面 HTML 和广告标签，再抽查首页及代表性业务路由。记录源码版本、发布任务、实际 URL、HTTP 状态、精确内容和检查时间；SP 显示成功、Git 已推送或本地测试通过均不能代替线上取证。必要时在正常请求及带缓存参数的请求下复查；不得为了消除 CDN 附加内容擅自关闭安全防护。

## 布局和发布证据

- 根据当前确认稿和实际断点检查详情页主按钮在平板、桌面和手机上的位置、可点击范围、长语言文案和 RTL；对 Playaro 本次要求，1000px 及以上的平板按钮放在右侧。不要把此站点的具体布局强加给其他品牌。
- 发布前确认源码提交、前端和 Worker 版本、SP API 与实际处理任务的 Worker 版本，先验证测试环境，再验证正式域名。记录任务 ID、实际请求路径、匹配规则、返回地址和打开结果，区分本地测试、代码推送、正式部署、真实回调和业务验收。
- 示例经验来自 2026-10-30 Playaro：95 个游戏的新详情、LP 和旧链接检查；SP 测试任务 53506 成功匹配 Turbo Traffic。该任务曾暴露“选择日语却返回主域名”的问题，不能把它当作修复后线上验收证据。
