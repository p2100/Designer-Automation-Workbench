# 如何展开审核清单

## 选择适用项

先取得候选结构清单和冻结规则版本，读取 [requirements.json](../contracts/requirements.json)。遍历实际路由的页面族，加入公共条款、对应页面条款以及所有成立的条件项。一个页面族的样例不代表同族所有应用身份/链接都正确。

`hard` 在适用时必须满足；`target` 是制作预算，偏离需理由与实际证据，不能把目标当未经验证的硬尺寸。`when` 为条件说明，不由程序自动判定；执行 Agent 必须给实际判断。只有条件不成立才可记 `not-applicable`，例如未启用搜索。空页面、缺图、断开的必备渠道不能用 not-applicable 消掉。

## 记录粒度与效率

- site：页面清单、英文范围、广告与候选等共享检查引用一次。
- entity：逐应用核对身份、平台/渠道、数据与媒体，可跨对应 detail/version 复用映射证据。
- page/component：同一页面、视口和状态合并查看，多条规则引用同一份证据；不重复导航取相同截图。

审核清单至少含规则 ID、实际页面/应用、候选身份、视口/状态、观察、证据与状态。使用 [review.json](../templates/review.json) 时先展开全部适用条款，不能把空数组当通过。

逐板块另对 module-data.json 核对图片角色、实际字段、排序/推荐依据和决策信息的主次关系。实看优秀参考的内容完整性与质感，再判断候选是否足够成熟；不能只看几何/溢出，或因为风格不同就判通过。用户否决的方向记录为否决，不被旧内部结论覆盖。

## 实际检查范围

PC 选择与交付相符的普通桌面宽度；手机至少393、320，并检查实际布局切换两侧。检查全页模块关系、普通/长名称、首项/中间/末行、截图原比例、按钮组、正文与推荐，不能只截一张首屏卡片。

遍历所有交付路由、内部链接、媒体引用及每个应用的渠道映射；视觉状态可按同构组件选代表样本，但必须覆盖真实存在的不同家族、长内容、异常和能力分支。代表取样不豁免逐实体身份/目的地检查。

执行正常导航/返回、画廊、菜单、分页和选用的搜索；还应检查空分类、缺图/失败、不可用渠道和404。下载跳转不等于安装或安全验证，按 data-and-channels 记录层级。外部渠道检查应尽量避免重复请求，可复用同一轮有效核对，但缓存不能证明已改变或过期目标仍有效。

## 状态与问题

状态为 `pass`、`issue`、`not-run`、`not-applicable`。pass 要有实际观察和证据，not-run 写明工具/范围限制；not-applicable 写明条件为何不成立。用户授权例外另外记录原话、范围和理由，不能借例外编造事实。

P0/P1/P2 的应用身份、目标、行为、布局或阅读问题应修正后再交付通过结论。按影响集中报告，再由作者统一返工；旧证据不得无检查复用到新候选。

本文件描述 Agent 的审核责任；本包没有实现一个自动认可视觉或伪造独立性的程序。
