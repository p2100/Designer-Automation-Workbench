# 逐板块数据、图片与内容组织

本文件从1.1.0起补足页面级清单未约束到的板块内容。字段定义与页面模块清单位于 [contracts/module-data.json](../contracts/module-data.json)，对应的参考事实见 [模块参考核对](../docs/module-reference-matrix-20261026.md)。数据完整、像素稳定与实际设计完成度分别审核。

## APP-MODULE-001 · hard · 每个已选模块

设计前为每个实际板块记录：业务用途、模块类型、实体/文章/分类数据源、选取或排序依据、条目数量、必需字段、已知条件字段、图片角色、主次关系、动作目标与PC/手机容量。不能只写“Banner、推荐、文章”就开始排版。

按模块合同读取数据，不给所有卡片套同一数据投影。字段缺失须标明未知；已有字段默认按合同使用，有意省略时写明与模块职责/容量有关的理由，不能用“可选”把真实数据全部闲置。

## APP-MODULE-002 · hard · 图片角色

独立Banner主视觉、App官方图标、真实产品截图、文章编辑封面是四种角色。图标存在不代表已制作Banner；把几张产品截图排在背景上，也不能自动登记为已完成独立推荐主视觉。选择图像主导的Banner时，必须有与推荐App/用途相关的独立主视觉和另外可辨认的App身份。

可以用原创编辑图像表达用途，需与官方产品截图分开记录，不能暗示是官方素材或该App的实际输出。产品截图保留真实平台与比例，用于详情画廊；文章封面服务具体选题，不能任取无关应用截图替代。

## APP-MODULE-003 · hard · 卡片字段与用途

普通推荐卡以App身份和决策信息为主：真实图标、名称、分类、已知评分/平台、已知下载量/平台及明确的详情入口。价格、开发者、短卖点按所选卡型/模块需要采用。不要用泛摘要替代已知的评分、分类、安装量等事实，也不把每张卡都塞成长介绍。

紧凑图标组可只保留身份与入口，分类可由组主题承担；功能工具推荐可以增加一条有用卖点；榜单行突出其排序指标；更新行突出真实版本与更新日期。不同用途各自选择合同内的投影，同一模块普通条目保持一致。

## APP-MODULE-004 · hard · 推荐、排序与数量

编辑推荐、按评分排序、按下载量区间排序、最近更新和新发行有不同依据。没有时间序列，不画增长/下降箭头；没有真实下载量，不叫下载榜。下载量为区间时保留区间，不冒充精确值；排名限定已选数据集，不借名称暗示全平台排名。

更新按对应平台的真实更新时间，发行按首次发行日期，二者不能互换。分类数量来自实际唯一成员。每组有明确目的，跨组可以合理重叠，但不得把同一集合改标题反复铺来填高度。参考站的模块数量/条数只是观察，任务按真实内容确定。

## APP-MODULE-005 · hard · 平台与字段来源

评分、评分人数、下载量、价格、版本、大小、更新时间等分别保留平台/来源。卡片可以使用清楚的公共来源说明配合必要平台标识；不能拼成一个看似统一的平台事实。没有Android版本号，不拿iOS版本填它；没有真实评论不生成用户评论。

绑定App的Banner、推荐卡、详情、version、文章内嵌卡使用同一实体映射。主视觉图不成为App功能或安全性声明的依据。

## APP-MODULE-006 · hard · 审核板块的实际内容质量

审核者逐板块对照：是否拿到了并正确使用数据、图片角色是否成立、用户是否能作出选择、信息量和空间是否匹配、主次阅读是否清楚、PC与手机是否各自设计。先看实际候选，再对照优秀参考的完成度；不是照抄参考颜色/按钮/排版，也不是只检查溢出后就给审美通过。

字段齐全仍可能视觉失败；“布局原创”不豁免低完成度。用户明确否决的首页/板块不能因旧方向审核通过继续作为已认可方向。修正应回应具体板块和证据，不靠再换主题色或增加空泛文案。
